# 系统设计与业务边界

青行使用 React 前端、Express 后端和 MySQL 数据库。前后端分别放在 `frontend/` 和 `backend/`；数据库结构、业务存储过程、查询及迁移放在 `database/`。运行和验证步骤见项目根目录的中文说明。

## 数据模型

八个核心实体为用户、车辆、停车区、骑行订单、支付、运维员工、调度任务和维修工单。调度车辆明细实现任务与车辆的多对多关系；其余支持表保存道路、库存快照、还车尝试、风险、调度建议、碳积分、审计和配置。当前共有 18 张表、4 个视图、2 个触发器和 38 个存储过程。

金额以整数分保存，每开始 30 分钟计 100 分；风险规则固定使用近 30 天窗口。旧库可能保留的 `pricing` 和 `risk` 配置行不参与上述规则，新库不再写入这些无效配置。坐标使用本地示意米制平面；停车区和还车坐标按米保留两位小数，围栏判断、存储证据与道路长度计算使用同一精度。数据库时间为 UTC，自动生成的时间由 MySQL UTC 表达式写入；运营日期及排行周期按北京时间计算。迁移保留已有时间，不推断历史服务器时区。碳积分使用追加流水，保存规则版本、当时的碳系数和积分比例及原因，不覆盖历史发放。旧流水缺失的积分比例保留为空；旧版已经舍入的碳系数无法还原。人工扣减不得使账户对应余额为负；同一调整请求编号只能重放完全相同的调整。

## 主要业务规则

1. 借车时检查账户、未结束骑行、未支付订单、车辆和停车区；同一用户及车辆只能有一笔活动订单。个人订单与支付历史按编号分页，进行中及待支付订单单独读取；订单导出按所选状态流式返回全部本人记录。
2. 还车检查定位时间、坐标、围栏及含调度预留的容量；拒绝时保存尝试，成功时计算路线和费用。个人及管理员复核页面可分页查看更早记录，个人查询仅返回本人记录。
3. 支付使用幂等键，订单支付与符合资格的积分发放在同一事务中完成；异常行程先复核。个人积分和减排显示流水净额，绿色行程次数与里程仅统计有效已支付订单的发放；流水按编号分页，调整记录不会增加行程次数。
4. 调度创建时预留车辆和目标车位，记录创建、出发及完成或取消后的两站库存。每个任务最多 100 辆，大额建议由数据库拆为多条，确认前逐条重新检查库存，也可以填写原因后不执行。升级前保存的超量建议在确认时标记为过期，提示重新生成；保存的建议按编号倒序分页，可继续查阅并处理更早的记录。
5. 报修车辆停止出租；管理员分配工单，具备相应岗位且被分配的运维员完成维修。工作台保留全部未完成工单和调度任务，已结束历史按编号分页；学生只能查看本人报修。
6. 风险规则结合近期工单、复发和维修间隔；异常短行程仅作为不计分的辅助线索。告警引用评估时已经创建的该车辆工单，排除退役车辆及未来工单；刷新时仅为需要新建的告警读取工单，避免重复传输已有告警的历史。风险告警按编号分页，历史记录仍可查看和处理；风险可以确认、关联工单、解决或排除。
7. 热点统计支持日期、工作日、小时和站点筛选。只依据截至查询时刻已存在、间隔不超过五分钟的相邻快照估计缺车和满车时长；相邻快照可以位于查询边界外，统计时裁剪到区间内，缺失采样不视为正常。
8. 路线支持有向道路、封闭状态以及最短、安全、舒适三种模式；排行榜默认不公开，按北京时间周或月统计；没有有效记录的用户看到“暂无排名”。默认昵称包含完整用户编号，少于四位时左侧补零；历史昵称和用户自行设置的昵称不会因升级而改写。

写事务重新检查操作者状态和角色，并使用数据库命名锁及行锁维护一致性。结构初始化和迁移在同一连接上持锁，覆盖建表、触发器和过程更新；MySQL 的结构变更会隐式提交，失败时必须检查并按备份恢复。业务事务和数据库迁移在命名锁获取或释放状态不确定时销毁连接；事务回滚失败、只读快照启动失败时也销毁连接，避免将异常连接返回连接池。命名锁串行化写事务，适用于课程规模；不能据此推断生产级吞吐能力。

## 权限与模拟边界

学生只能操作自己的行程及报修；运维员处理分配给自己的任务和具备岗位权限的风险；管理员管理基础资料和复核工作流。地图、道路属性、定位、支付与碳系数均为教学模拟，风险评分不是经过真实数据验证的预测模型。

原始课程材料未全部提供；已依据仓库内的需求、接口和课程设计文档实现并测试，不对缺失材料作完整性承诺。
